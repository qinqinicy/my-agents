## 核心问题修复记录

### 2026-04-22

**问题 1: StreamUI 看不到视频流**
- 原因: ZLM Docker 网络模式为 bridge，导致跨容器通信失败
- 解决: 改用 `--network host` 模式启动容器

**问题 2: addStreamProxy API 返回 "Required parameter missed: vhost"**
- 原因: 缺少 `vhost=__defaultVhost__` 参数
- 解决: 添加该参数后成功

**问题 3: HLS 录像不生成 .ts 文件**
- 原因: `hls_demand=1`（按需模式）改为 `hls_demand=0`（连续录制）
- 解决: 配置 `hls_demand=0` 和 `hls_save_path=/opt/media/www`

**问题 4: StreamUI 访问录像返回 "/opt/media/bin/www/record directory not found"**
- 原因: StreamUI 代码写死了 `/opt/media/bin/www` 路径
- 解决: `ln -sf /opt/media/www /opt/media/bin/www`

### 2026-04-23

**问题 5: addStreamProxy 无法拉取 RTMP 流**
- 原因: ZLM addStreamProxy 对某些 RTMP URL 格式校验严格，直接拉取失败
- 解决: 使用 ffmpeg 中转方案 - ffmpeg 从外部拉取 RTMP，推送到 ZLM 本地 rtmp://127.0.0.1/live/{stream}

**proxy_example 流接入方案**
- 源地址: `rtmp://10.129.80.244:1935/proxy_example`
- 中转方式: ffmpeg 推送到 ZLM 本地 `rtmp://127.0.0.1/live/proxy_example`
- systemd 服务: `/etc/systemd/system/ffmpeg-proxy.service`
- ffmpeg 路径: `/opt/media/tools/ffmpeg`（从 `/usr/local/bin/ffmpeg` 复制）

**问题 6: StreamUI 看不到 proxy_example 录像**
- 原因: ffmpeg 推送到 live 应用，录像在 `/opt/media/www/live/proxy_example/`
- 解决: `ln -sf /opt/media/www/live/proxy_example /opt/media/www/record/proxy_example`

## 经验教训

- ZLM Docker 必须使用 `--network host` 否则跨网络通信失败
- addStreamProxy 必须传 `vhost=__defaultVhost__`
- ZLM addStreamProxy 对某些 RTMP URL 格式无法拉取（报错 "rtmp url非法" 或 "end of file"），此时用 ffmpeg 中转
- **ZLM FFmpegSource 在 Docker + seccomp=2 环境下无法 fork 进程**（2026-04-24 发现）—— 日志静默，FFmpeg 进程从不启动
- **SRS ingest 是 ZLM FFmpegSource 的可行替代**（2026-04-24 验证）
- ffmpeg 中转方案：推送到 `rtmp://127.0.0.1/live/{stream}`，ZLM 接收后自动录制
- systemd 服务管理 ffmpeg 中转，确保断线自动重启（Restart=always, RestartSec=5）
- ffmpeg 静态二进制需要复制到 `/opt/media/tools/` 供 systemd 使用
- rclone serve 默认绑定 IPv6，需加 `--bind 0.0.0.0` 绑定 IPv4
- rclone sync 正在录制的文件会报 "sizes differ"，需排除 `.` 开头的临时文件 `--exclude "**/.*"`
- SRS `dvr_path` 的 `[datetime]` 变量在 5.0.213 版本有 bug，不展开为实际时间戳

## 2026-04-27 Oryx Web 管理界面部署

### Oryx（Oryx Stack）
- 镜像：ossrs/oryx:5
- 作用：SRS 的社区 Web 管理界面（Go + React）
- 外部依赖：Redis（127.0.0.1:6379，密码 avicitbdp）

### Oryx Docker 部署
```bash
docker run -d --name oryx \
  --network host \
  -v /opt/media/oryx/redisconf/redis.conf:/usr/local/oryx/platform/containers/conf/redis.conf \
  -e SRS_API_PORT=1985 -e SRS_RTMP_PORT=1935 -e SRS_API_SECRET=mysecret123 -e SRS_SERVER_PORT=1935 \
  registry.cn-hangzhou.aliyuncs.com/ossrs/oryx:5
```

### 问题 1：bootstrap 循环调用 start_redis
- 现象：容器内出现无数 `bash /usr/local/oryx/platform/bootstrap` 进程
- 原因：start_redis 中用 `exec /usr/local/oryx/platform/bootstrap` 替换进程，导致递归
- 解决：不调用 exec，直接返回，bootstrap 继续执行后续 SRS 启动逻辑

### 问题 2：load_env 文件不存在
- Oryx 容器内 `/usr/local/oryx/platform/auto/load_env` 不存在
- bootstrap 从 `.env` 文件读取环境变量，不依赖 `load_env`

### 问题 3：Oryx 8080 端口绑定失败（errno=98）
- Oryx Go 服务监听 0.0.0.0:8080，bind 失败
- ss 显示无占用，但实际无法绑定
- 可能与容器网络模式或 SRS 残留有关

### 经验教训
- Oryx start_redis 是 bootstrap 的前置钩子，不能替代 bootstrap 进程
- 正确做法：start_redis 加载 `.env` 环境变量后直接返回
- `load_env` 文件在 Oryx 容器内不存在，实际从 `containers/data/config/.env` 读取
